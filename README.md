# nopt-integration-test

TestPyPI-only integration fixture for [nopt](https://github.com/nhairs/nicks-opinionated-python-package-publishing-tool). The `release.yml` workflow is the end-to-end smoke test: it exercises nopt, GitHub Actions, trusted publishing to TestPyPI and GitHub releases. Agents or cross-repository automation can drive test batches and assert successful or expected-failure outcomes. Nopt's own repository owns its regression tests.

Package dependencies and nopt itself come from PyPI; this repository's distributions must only be uploaded to TestPyPI.

## Develop the fixture

Requires Python 3.11+, Git and uv.

```sh
uv sync --group dev
uvx --with tox-uv tox -e lint,py313
uvx --with tox-uv tox
```

Tox covers CPython 3.11–3.15 and PyPy 3.11–3.12. The package uses setuptools and the published setuptools-git-metadata plugin, replacing the legacy template's dev.sh/Docker build chain. Its committed runtime loader is generated by that plugin. CI validates the fixture's packaging, import, formatting and types; it does not run a second nopt regression suite.

## Run a live TestPyPI batch

After the setup checklist is complete:

1. Create a branch for the batch, choose a new canonical project version, and update the matching base-version changelog section. Never reuse an uploaded version. Pre/final releases must satisfy the configured main-branch policy; dev releases permit test branches by default.
2. Select the nopt requirement in all four release commands: a published pin such as `nopt==0.1.0.dev0`, or `nopt @ git+https://github.com/nhairs/nicks-opinionated-python-package-publishing-tool@COMMIT` to test a source revision. Keep those requirements consistent.
3. Run the relevant checks and merge the batch PR when appropriate. See AGENTS.md for autonomy and human-review boundaries.
4. Tag the intended commit as `v<project.version>` and push the tag. Branch PRs and release tags serve separate purposes. If the tag was created with GITHUB_TOKEN, explicitly dispatch `release.yml` at that tag because its push event does not start a new workflow.
5. Inspect the run's jobs/diagnostics, TestPyPI distribution files and GitHub release. Assert the intended success or failure and any expected absence of publication, then retain run/artifact links as batch evidence. Increment the version for the next batch.

The workflow supports both tag pushes and explicit dispatch at an existing tag:

```sh
gh workflow run release.yml --repo nhairs/nopt-integration-test --ref TAG
gh run list --repo nhairs/nopt-integration-test --workflow release.yml
```

Use dispatch for expected-failure tags excluded by the `v*.*.*` push filter (for example, a two-component tag). Nopt still validates canonical versions. Dispatch becomes available after the workflow is merged into the default branch. It does not add retry/recovery support; inspect any previous run and remote state before dispatching the same tag again.

The release workflow runs nopt preflight, the reusable `test.yml` fixture CI, build, package-publication preflight, PyPA trusted publishing and GitHub-release publication. All nopt steps read the TestPyPI target and username from `[tool.nopt]` in pyproject.toml (from its original bundled copy during publishing). The upload action uses `https://test.pypi.org/legacy/`; the unattended GitHub deployment environment is `testpypi`. Dev/pre/final GitHub releases are enabled so dev batches exercise that path too.

Uv selects a compatible Python interpreter for release commands. PyPA adds attestation sidecars to its disposable downloaded dist directory; publication evidence includes those files. The stored build artifact stays unchanged, and the GitHub-release job downloads it afresh. GitHub publication verifies TestPyPI file hashes before staging and publishing the release.

## Automate batches and expected failures

A cross-repository caller needs a GitHub App or fine-grained token with Actions write access here to dispatch the release workflow, plus suitable write permissions if it creates test PRs/branches/tags. Its ordinary GITHUB_TOKEN is scoped to the caller repository. An agent with repository access can perform the same operations directly. Events created using a repository's GITHUB_TOKEN generally do not trigger new workflows; explicit dispatch is the supported alternative for such a tag.

The repository currently supplies the release fixture and workflow. A batch controller that allocates versions/tags, dispatches runs, waits and asserts scenario-specific outcomes is still to be built. Expected failures should target the live workflow/TestPyPI boundary (for example, refusing an already-published version), with explicit checks for the intended rejection and any unintended external changes. A red workflow alone is not proof that the expected failure occurred.

Keep failed live scenarios isolated on test branches/tags and retain their run/evidence links. Nopt currently binds bundles to the originating run attempt and rejects existing GitHub releases/drafts. Inspect partial uploads and drafts before any retry. Tag recreation after a workflow repair does not make an uploaded version reusable.

- Choose cross-repository App/token credentials if needed, then run the first unique-version live batch and verify TestPyPI/GitHub outcomes. Add the batch controller and live expected-failure assertions as follow-up work. No live publication is claimed yet.
