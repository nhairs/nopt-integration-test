# nopt-integration-test

TestPyPI-only integration fixtures for [nopt](https://github.com/nhairs/nicks-opinionated-python-package-publishing-tool). This repository supports agent-driven tests and GitHub Actions. Package dependencies and nopt itself come from PyPI; this repository's distributions must only be uploaded to TestPyPI.

## Develop and run scenarios

Requires Python 3.11+, Git and uv.

```sh
uv sync --group dev
uvx --with tox-uv tox -e lint,py313
uvx --with tox-uv tox
```

Tox covers CPython 3.11–3.15 and PyPy 3.11–3.12. The package uses setuptools and the published setuptools-git-metadata plugin, replacing the legacy template's dev.sh/Docker build chain. Its committed runtime loader is generated by that plugin.

`tests/test_scenarios.py` exercises nopt through its CLI against temporary local Git repositories. It covers an actual successful bundle build and specific expected failures. These tests may read TestPyPI metadata, but do not upload packages, create remote tags or publish GitHub releases. Build tools/dependencies require network access unless cached.

To test another nopt revision without changing the default dependency pin:

```sh
uv pip install 'nopt @ git+https://github.com/nhairs/nicks-opinionated-python-package-publishing-tool@COMMIT'
uv run --no-sync python -m pytest tests
```

The `Integration scenarios` workflow supports manual dispatch and reusable workflow calls. A caller in another repository can use `nhairs/nopt-integration-test/.github/workflows/scenarios.yml@COMMIT` with required `integration-ref: COMMIT` set to that same integration-repository commit. This explicitly checks out the integration fixtures rather than the caller's repository. Alternatively, dispatch it with a token authorized for Actions writes in this repository:

```sh
gh workflow run scenarios.yml --repo nhairs/nopt-integration-test \
  -f 'nopt-requirement=nopt==0.1.0.dev0'
```

The caller's ordinary GITHUB_TOKEN is scoped to its own repository; cross-repository dispatch requires suitable GitHub App or fine-grained-token access. The scenario workflow has read-only repository permissions, no deployment environment and no upload-to-index step. It retains a JUnit report for 90 days. Dispatch becomes available after this workflow is merged into the default branch. Live publishing tests are a separate flow below, not part of these read-only scenarios.

## Run a live TestPyPI batch

After the setup checklist is complete:

1. Create a branch for the batch, choose a new canonical project version, and update the matching base-version changelog section. Never reuse an uploaded version. Pre/final releases must satisfy the configured main-branch policy; dev releases permit test branches by default.
2. Run the relevant checks and merge the batch PR when appropriate. See AGENTS.md for autonomy and human-review boundaries.
3. Tag the intended commit as `v<project.version>` and push the tag. Branch PRs and release tags serve separate purposes. If the tag was created with GITHUB_TOKEN, dispatch `release.yml` explicitly at that tag (`gh workflow run release.yml --ref TAG`) because its push event does not start a new workflow. Dispatch only fresh, unpublished batches; it does not add retry/recovery support.
4. Inspect the `Publish release` run, TestPyPI distribution files and GitHub release, and retain the run/artifact links as batch evidence. Increment the version for the next batch.

The release workflow is adapted from nopt's merged workflow template. It runs nopt preflight, CI, build, package-publication preflight, PyPA trusted publishing and GitHub-release publication. Every nopt command explicitly selects TestPyPI; the upload action hardcodes `https://test.pypi.org/legacy/`. The GitHub deployment environment is deliberately named `pypi` and has no human approval gate. Dev/pre/final GitHub releases are enabled so dev batches exercise that path too. GitHub publication verifies TestPyPI file hashes before staging and publishing the release.

Nopt is pinned consistently in all release jobs. `scenarios.yml` can test an alternate nopt requirement without changing the release workflow. Update the release-job pins together when testing another nopt version in a live batch.

Expected-failure live scenarios should run on isolated test branches/tags and record the intended rejection plus any remote state changes. A failed upload is not automatically recoverable: nopt currently binds bundles to the original run attempt and rejects existing GitHub releases/drafts. Inspect partial uploads and drafts before any retry. Tag recreation after a workflow repair does not make an uploaded version reusable.

## Finish setup

- The owner confirmed TestPyPI username `nhairs-test`; the configured project name is therefore `nopt-integration-test-nhairs-test`. The release guard rejects missing or placeholder suffixes before building or uploading.
- Owner confirmed the **TestPyPI** pending publisher is configured: owner `nhairs`, repository `nopt-integration-test`, workflow filename `release.yml`, environment `pypi`, project `nopt-integration-test-nhairs-test`. The first live batch must verify this configuration through an actual OIDC upload. No production publisher or token is needed.
- Review and merge the initial setup PR, including AGENTS.md and CODEOWNERS. That PR requires human feedback. No release tag is created by setup.
- Configure main-branch rules: prevent deletion and force pushes, require PRs and successful CI, and require code-owner review for AGENTS.md/CODEOWNERS changes. Keep ordinary test branches/tags manageable by agents, without mandatory human review for every test PR. Existing `pypi` environment is already unattended. Main is currently unprotected, and this session's GitHub credential does not expose admin access to change the rules.
- Decide how cross-repo callers authenticate for dispatch and how they retrieve/assert completion. A reusable read-only call needs no repository dispatch token; unattended tag/PR operations need a suitable write token or GitHub App. Events created using a repository's GITHUB_TOKEN generally do not trigger new workflows, so use an appropriate App/token when a pushed tag must launch the release workflow.
- Run the first unique-version live batch, verify the successful TestPyPI/GitHub outcomes, then add live expected-failure cases with explicit assertions and retained evidence. Local/CI scenarios are prepared; no live publication is claimed yet.

The bootstrap adapts the package-template layout and T0029 modernization conventions. Configuration and executable workflows are the source of truth; keep AGENTS.md limited to authority and repository rules.
